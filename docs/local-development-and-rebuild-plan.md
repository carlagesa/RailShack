# RailShack: local application and deployment rebuild plan

## What this repository contains

RailShack is a train-booking application split into 50 HTTP services: 22 Go, 18
Node.js, 6 Python, and 4 Java services. The browser talks to `frontend` on
port 9050. `frontend` forwards API requests through `api-gateway` on port 9039,
which routes them to the other services. `services.json` is the catalog of
service names, language, domain, and local port.

The shared kits in `libs/` provide health endpoints, JSON logging, metrics,
inter-service calls, and optional persistence helpers. PostgreSQL is the
durable store when `DATABASE_URL` is configured; Redis is an optional cache
when `REDIS_ADDR` is configured. Without those settings, some services use
in-memory data, which is lost when the process exits.

The runbook described a separate production layer: EKS Auto Mode, Helm, AWS
load balancers, ACM, Route 53, EBS, GitHub Actions, GitHub OIDC, GHCR, and
Prometheus/Grafana. The application code does not call AWS APIs directly. Those
AWS services provision the Kubernetes environment and its ingress, storage,
identity, and release process; they are not application dependencies.

## Run the application locally

The local runner uses source code, not a container image. Run it from Git Bash
or WSL on Windows (or another Bash environment) with Go 1.24, Node.js 22,
Python 3.13, JDK 21, Python 3, and curl available.

1. (Optional, but recommended for persistence and cache behavior) Start a local
   PostgreSQL 16 database and Redis 7 instance. They can be installed directly
   or run as local-only containers. Create a database named `railshack` and a
   user/password for the app.
2. Set `DATABASE_URL` to that PostgreSQL database and `REDIS_ADDR` to the Redis
   host and port in the same Bash shell. If unset, the app uses its in-memory
   paths where available.
3. From the repository root, run `bash scripts/start-services.sh`. It compiles
   Go and Java services, starts all 50 services on ports 9001-9050, and waits
   for their `/healthz` endpoints. Logs and PID files are written under `.run/`.
4. Open `http://localhost:9050` or run
   `bash scripts/smoke-test.sh http://localhost:9050` for the end-to-end
   sign-up, search, booking, PNR, trip-history, and cancellation flow.
5. To stop the locally started processes, send `TERM` to the PIDs recorded in
   `.run/pids/`. Stop any local PostgreSQL/Redis processes separately.

The test-only GitHub Actions workflow follows the same path: it starts
PostgreSQL and Redis as test dependencies, launches all services from source,
and runs the smoke test. It does not publish images or deploy anything.

## Rebuild deployment locally, in learning stages

The target is a local learning environment only. There must be no AWS account,
real AWS credentials, production DNS, or public image registry involved. Do not
run commands using a default AWS profile. Before wiring a CLI or controller to
an emulator, explicitly configure its endpoint to loopback and use only the
credentials generated by that local emulator instance.

The target emulator is [AWS Emulator v1.0.322](https://github.com/aws/aws-emulator/releases/tag/v1.0.322).
It is an AWS API emulator, not a local AWS account or a turnkey Kubernetes
distribution. AWS documents a local HTTPS API endpoint and a Docker setup for
Windows; there is no prebuilt Docker image. The package version corresponding
to release tag `v1.0.322` is `1.0.322.1`. As of 2026-11-21, the published
package list already includes newer releases, so use the pinned package URL
below only to reproduce this lab.
AWS says security fixes are published only in the latest release; keep this
older version loopback-only and use emulator credentials, never real ones. The
emulator keeps resource state in memory and drops it when stopped, represents
one account and one Region per instance, and does not evaluate IAM policies.
Fidelity differs by service and operation, so consult the [official fidelity
guide](https://docs.aws.amazon.com/emulator/latest/userguide/fidelity.html) and
the score file published with the pinned release.

The distinction is especially important for EKS. In v1.0.322, EKS
`CreateCluster` and `CreateNodegroup` model AWS control-plane API resources; they
do not give this project a connected Kubernetes cluster with schedulable worker
nodes. The [release's CreateCluster implementation](https://github.com/aws/aws-emulator/blob/v1.0.322/services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/create_cluster.rs)
records cluster state, while its initial record has no provisioned control
plane. The [CreateNodegroup implementation](https://github.com/aws/aws-emulator/blob/v1.0.322/services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/create_nodegroup.rs)
records the node-group API resource, not running worker VMs. The release score
snapshot has 232 passing of 404 EKS-tagged fidelity
test units; only 2 of 7 `CreateCluster` test units pass. See the [release score
snapshot](https://github.com/aws/aws-emulator/releases/download/v1.0.322/scores.json.gz).
Therefore, use kind (or another local Kubernetes distribution) for the actual
RailShack pods, and use AWS Emulator to learn and test supported AWS API
behavior separately.

### Stage 0 — start AWS Emulator safely on Windows

1. Install and start Docker Desktop. Follow the [official AWS Emulator Docker
   instructions](https://docs.aws.amazon.com/emulator/latest/userguide/getting-started-docker.html)
   to build the emulator image. In its Dockerfile, replace the example
   `LTS/latest` package URL with this x86_64 package URL for the requested
   release:

   ```text
   https://downloads.aws.com/aws-emulator/packages/aws-emulator/LTS/aws-emulator-1.0.322.1-1-x86_64.rpm
   ```

   Verify the installed version with `aws-emulator -v` before continuing.
2. Run the container with its API port bound only to loopback (`127.0.0.1`),
   using the documented default port 9297. Mount
   `$env:USERPROFILE\.aws\emulator` so the emulator-generated credentials,
   config, and TLS CA certificate are available to Windows tools. Once the
   version-pinned image is built, the Windows PowerShell run command is:

   ```powershell
   New-Item -ItemType Directory -Force "$env:USERPROFILE\.aws\emulator"
   $port = 9297
   docker run --rm --memory=2g --memory-swap=2g `
     -p "127.0.0.1:${port}:${port}" `
     -v "$env:USERPROFILE\.aws\emulator:/home/emulator/.aws/emulator" `
     aws-emulator -p $port
   ```

   The [service overview](https://docs.aws.amazon.com/emulator/latest/userguide/what-is-service.html)
   documents Windows as a Docker-based install.
3. In a dedicated PowerShell window, configure the AWS CLI environment for
   `https://127.0.0.1:9297`: set `AWS_ENDPOINT_URL`,
   `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`, `AWS_CA_BUNDLE`,
   `AWS_EC2_METADATA_DISABLED=true`, and
   `AWS_DISABLE_HOST_PREFIX_INJECTION=true`. Use the emulator-generated
   credentials and one Region (`us-west-2` matches the release's regional
   fidelity test Region). For example:

   ```powershell
   $port = 9297
   $emulatorDir = "$env:USERPROFILE\.aws\emulator\$port"
   $env:AWS_ENDPOINT_URL = "https://127.0.0.1:$port"
   $env:AWS_SHARED_CREDENTIALS_FILE = "$emulatorDir\emulator_credentials"
   $env:AWS_CONFIG_FILE = "$emulatorDir\config"
   $env:AWS_CA_BUNDLE = "$emulatorDir\ca.pem"
   $env:AWS_EC2_METADATA_DISABLED = "true"
   $env:AWS_DISABLE_HOST_PREFIX_INJECTION = "true"
   $env:AWS_REGION = "us-west-2"
   $env:AWS_DEFAULT_REGION = "us-west-2"
   Remove-Item Env:AWS_ACCESS_KEY_ID, Env:AWS_SECRET_ACCESS_KEY, Env:AWS_SESSION_TOKEN, Env:AWS_PROFILE `
     -ErrorAction SilentlyContinue
   ```

   Use `--endpoint-url https://127.0.0.1:9297` on AWS CLI calls as an
   additional guard. The emulator's [SDK setup instructions](https://docs.aws.amazon.com/emulator/latest/userguide/point-sdk-to-emulator.html)
   explain the generated credentials, TLS certificate, and endpoint variables.
4. Confirm the local HTTPS health endpoint using the emulator CA before making
   API calls. Keep endpoint configuration in the same shell as every AWS CLI
   test:

   ```powershell
   curl.exe --cacert "$env:AWS_CA_BUNDLE" https://127.0.0.1:9297/__admin/health
   ```
5. Keep in mind that emulator resources exist only in its memory and disappear
   on restart. Do not use it as the backing store for PostgreSQL, Redis, or
   Kubernetes application data. Its default anonymous usage/error telemetry
   can be disabled as described in the [official telemetry guide](https://docs.aws.amazon.com/emulator/latest/userguide/telemetry.html).

**Checkpoint:** the health request succeeds against `127.0.0.1:9297` with the
emulator CA, and the same AWS CLI context cannot fall back to real credentials
or a real AWS endpoint.

### Stage 1 — prove the bare app still works

1. Start PostgreSQL and Redis locally, set `DATABASE_URL` and `REDIS_ADDR`, and
   use the source-based runner.
2. Verify all 50 `/healthz` checks, then run the smoke test through
   `http://localhost:9050`.
3. Keep this as the baseline when adding deployment files back. It separates
   application bugs from container, Kubernetes, and emulator issues.

**Checkpoint:** the smoke test passes against local data services and all
services are visible in `/api/platform/status`.

### Stage 2 — restore container packaging

The reusable runtime recipes in `docker/` build each service from the
repository root. That build context is required because the services import
their shared language kits from `libs/`. `.dockerignore` omits local state,
generated files, dependencies, and environment files while retaining the
service catalog and shared kits.

1. Build and run one service first. For example, from the repository root:

   ```bash
   docker build -f docker/Dockerfile.node \
     --build-arg SERVICE=user-profile \
     -t railshack/user-profile:dev .
   docker run -d --rm --name user-profile \
     -p 9002:8080 railshack/user-profile:dev
   for attempt in $(seq 1 30); do
     curl -fsS http://localhost:9002/healthz >/dev/null && break
     sleep 1
   done
   curl -fsS http://localhost:9002/healthz
   curl -fsS http://localhost:9002/readyz
   curl -fsS http://localhost:9002/metrics
   curl -fsS http://localhost:9002/api/user-profile/demo
   docker logs user-profile
   docker stop user-profile
   ```

   Each container listens on port 8080; the host port is the service's port
   from `services.json`. The Go, Java, and Python images run as non-root users;
   the Node base image's `node` user is used as well.
2. Build all 50 images locally. This Bash loop reads the service names and
   runtimes from `services.json` and selects the matching shared Dockerfile:

   ```bash
   while read -r name lang; do
     case "$lang" in
       go)     dockerfile=docker/Dockerfile.go ;;
       node)   dockerfile=docker/Dockerfile.node ;;
       python) dockerfile=docker/Dockerfile.python ;;
       java)   dockerfile=docker/Dockerfile.java ;;
       *) echo "Unsupported runtime: $lang" >&2; exit 1 ;;
     esac
     docker build -f "$dockerfile" --build-arg "SERVICE=$name" \
       -t "railshack/$name:dev" .
   done < <(python3 -c \
     'import json; [print(s["name"], s["lang"]) for s in json.load(open("services.json"))]')
   ```

   Do not push images to GHCR or any public registry. Do not set `PORTS_FILE`
   inside containers: without it, the shared kits use service DNS names
   (`http://<service>:8080`) rather than the source-runner's localhost ports.
   When running all services together, place them on one Docker network and
   name each container/service after its catalog entry. Publish the frontend's
   port to the host; service-to-service calls should stay on that network.
   Configure frontend's `SERVICES_FILE=/app/services.json` if needed.

**Checkpoint:** the frontend container can reach the API gateway and all
service containers can reach their dependencies by a local network name.

### Stage 3 — bring up local Kubernetes

1. Start a local Kubernetes cluster with kind (or another selected local
   cluster) and a private local image registry. Connect the registry to the
   cluster and load or push the `:dev` images only to that registry.
2. Learn the Kubernetes primitives in a small slice first: namespace,
   ConfigMap, Secret, Deployment, Service, readiness/liveness probes, resource
   requests, and logs. Start with frontend, API gateway, one downstream
   service, PostgreSQL, and Redis.
3. Add the remaining services in groups, reading their target ports from
   `services.json`. Use Kubernetes service DNS instead of host ports for
   service-to-service traffic.
4. Add local persistent volumes for PostgreSQL and check data survives a pod
   restart. Use a local storage class; do not assume EBS exists merely because
   an AWS emulator exposes an EBS API.

**Checkpoint:** `kubectl get pods,services -n railshack` is healthy and the
smoke test reaches the app through a local port-forward.

### Stage 4 — recreate the release chart without cloud assumptions

1. Rebuild a Helm chart only after plain Kubernetes manifests are understood.
   Start with Deployments and Services generated from a single service catalog
   where practical; keep the application behavior independent of Helm.
2. Add PostgreSQL, Redis, secrets, probes, resource requests/limits, and a
   single-replica local profile. Fifty services consume meaningful memory, so
   measure the machine before increasing replicas.
3. Add a local ingress controller if a stable local hostname is useful. Begin
   with `localhost`/port-forward; use a local-only hostname and hosts-file
   mapping before attempting TLS. A cloud ALB integration is a separate step.

**Checkpoint:** `helm template` renders valid local Kubernetes resources, an
install/upgrade is repeatable, and a failed upgrade can be rolled back locally.

### Stage 5 — integrate only the AWS APIs the emulator really supports

1. First use the emulator's EKS and EC2 APIs as an API-learning exercise:
   create an emulated VPC, subnets in at least two availability zones, and a
   security group; create an emulated IAM role; then call EKS `CreateCluster`
   and `DescribeCluster` through the local endpoint. This teaches the AWS
   resource relationships without provisioning anything in AWS.
2. Treat a successful EKS `ACTIVE` response as an emulated AWS resource state,
   not proof that `kubectl` can reach a functioning cluster. Do not point
   `kubectl` or Helm at the returned EKS endpoint unless a separate test proves
   that it serves the Kubernetes APIs needed by the workload. Keep kind as the
   actual Kubernetes control plane for RailShack.
3. Exercise ECR, ELBv2, ACM, Route 53, and EBS APIs one at a time only after
   checking the v1.0.322 fidelity scores and required operations. Use a local
   image registry, local ingress controller, local TLS/hosts-file setup, and
   local storage class for working workloads. API-level emulation does not
   automatically connect the AWS Load Balancer Controller or EBS CSI driver to
   the emulator.
4. Do not recreate the runbook's GitHub OIDC deployment login as a security
   exercise: AWS Emulator does not evaluate IAM policies, so it cannot validate
   the real OIDC trust policy or authorization boundary. Keep deployment
   commands in a local shell with the endpoint configured; never use GitHub
   secrets, a real AWS profile, or real AWS credentials.

**Checkpoint:** RailShack runs in kind, while AWS API exercises demonstrably
target only the emulator. Each emulated resource is clearly distinguished from
the corresponding live AWS or Kubernetes resource.

### Map the original AWS deployment to local tools

| Original deployment piece | Local learning version |
|---|---|
| EKS Auto Mode cluster | AWS Emulator for EKS API resource calls; kind for the real local Kubernetes API and RailShack pods |
| EKS managed node groups / Auto Mode compute | No emulated worker capacity; keep kind node count fixed and use HPA only to observe pod scaling |
| EC2 VPC, subnets, security groups | Emulated EC2 API resources, created only as inputs to EKS API exercises |
| IAM role and GitHub OIDC | Emulator-generated CLI credentials for local API calls; skip OIDC because IAM policy evaluation is not emulated |
| ECR and GHCR images | Local container registry; do not push images to AWS or GitHub |
| AWS Load Balancer Controller and ALB | Local ingress controller, or `kubectl port-forward` for the first iteration |
| ACM certificate and Route 53 records | Local-only TLS certificate and hosts-file name; no public DNS |
| EBS CSI volume for PostgreSQL | kind's local storage class / persistent volume; keep the DB separate from the emulator's in-memory state |
| Helm release and monitoring | Rebuilt Helm chart, Prometheus, and Grafana installed into kind after the app works |
| GitHub Actions CD | Local build/deploy commands with no cloud credentials; the remaining GitHub Actions workflow only tests the source app |

For orientation, a Kubernetes **Deployment** keeps a desired number of app
pods running; a **Service** gives those pods a stable in-cluster name and port;
a **ConfigMap** holds non-secret settings; a **Secret** holds credentials; a
**PersistentVolumeClaim** requests storage; and an **Ingress** routes HTTP from
outside the cluster to a Service. Learn these against kind before layering in
Helm or AWS API calls.

### Stage 6 — add observability and repeatable tests

1. Install Prometheus and Grafana locally with Helm after the app works in
   Kubernetes. Scrape the existing `/metrics` endpoints and then add database
   and cache exporters if useful.
2. Restore the service dashboards and alert rules as a separate observability
   exercise; they are not required to run the booking app.
3. Keep CI application tests separate from image publishing and deployment.
   Add local image-build and Helm-render checks only when those artifacts are
   reintroduced.
4. Run smoke tests after each change. Then test pod restarts, database
   persistence, a bad image/failed rollout, and rollback. Run any small bounded
   load test against the application in kind, never against AWS Emulator; AWS
   documents that the emulator is for test runs and is not tested for load
   testing or long-running use.

**Checkpoint:** a clean local start, upgrade, smoke test, and teardown can be
repeated without contacting real AWS services.

## How this differs from the original runbook

The original target used EKS Auto Mode, ALB ingress, ACM certificates, Route 53,
EBS volumes, GitHub OIDC, GHCR, and a GitHub Actions CD pipeline. Those are
removed from the working tree for this learning baseline. Their local
reintroduction order is: images, kind-based Kubernetes resources, local
ingress/storage, AWS Emulator API exercises, then monitoring and release
automation. The emulator models AWS API state; kind runs the application pods.
Real AWS deployment is intentionally outside this plan.
